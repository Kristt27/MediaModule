# План Доработки MediaModule За 15 Дней

## Исходная ситуация

- Решение собирается без ошибок.
- Базовая архитектура уже есть: `Worker`, `Desktop`, `Application`, `Infrastructure`, `Domain`.
- По факту сквозной сценарий пока не доведен до рабочего состояния.
- Реальные API `ELMA` будут использоваться, значит интеграцию нужно закладывать как обязательную часть работ, а не как опцию.

## Критичный вывод после первичной диагностики

Сначала нужно не "допиливать функции", а восстановить базовый pipeline:

`сохранение файла -> событие FileSystemWatcher -> оркестратор -> проверка -> лог -> UI`

Без этого любые доработки по тегам, журналу и интеграциям не дают результата.

Дополнительно уже виден минимум один источник проблемы:

- в `src/MediaModule.Worker/appsettings.json` каталог мониторинга сейчас задан через `Module.MonitoredDirectories`,
- при этом `RootDirectory` указывает на `demo\\Design`,
- а `MonitoredDirectories` указывает на `%USERPROFILE%\\Desktop`,
- значит модуль слушает не рабочую директорию макетов, а другой путь.

Итог: пользователь может сохранять файл "в нужную папку", а модуль ее просто не отслеживает.

## Цель на 15 дней

Довести проект до состояния, в котором:

- модуль стабильно ловит сохранение файлов в рабочих каталогах;
- выполняется полный сценарий проверки и обработки;
- интеграция с `ELMA` работает на реальном API;
- UI позволяет просматривать журнал и результаты обработки;
- есть тесты на критичную бизнес-логику;
- есть воспроизводимый сценарий демонстрации для защиты.

## Приоритеты

### Блок A. Обязательный фундамент

1. Рабочее обнаружение сохранения файлов.
2. Корректная конфигурация путей мониторинга.
3. Стабильная обработка событий без ложных срабатываний и потерь.
4. Запись результатов в `SQLite`.
5. Отображение результатов в `Desktop`.

### Блок B. Обязательная бизнес-ценность

1. Реальная интеграция с `ELMA`.
2. Проверка имени и пути на основе данных заказа.
3. Обработка дубликатов.
4. Управление тегированием и сохранением результатов.

### Блок C. Защитный контур

1. Тесты.
2. Демонстрационные сценарии.
3. Инструкция запуска.
4. Финальная стабилизация.

## План по дням

### День 1. Восстановить обнаружение файлов

- Проверить фактические рабочие каталоги, которые должны отслеживаться.
- Исправить конфигурацию `Module.MonitoredDirectories` и логику выбора каталогов.
- Добавить понятные стартовые логи: какие именно пути слушаются.
- Проверить сценарии `Created`, `Changed`, временные файлы, сохранение через графические редакторы.
- Подтвердить, что файл реально доходит до `FileProcessingOrchestrator`.

Результат дня:

- сохранение тестового файла стабильно вызывает обработку;
- есть подтверждение в логах и в БД.

### День 2. Стабилизировать базовый pipeline

- Проверить debounce и повторные события `FileSystemWatcher`.
- Убрать лишний шум от нерелевантных папок и временных файлов.
- Проверить обработку блокировок файла, если редактор еще не завершил запись.
- Добавить диагностику причин пропуска файла.

Результат дня:

- модуль стабильно обрабатывает реальные сохранения без хаотичного поведения.

### День 3. Проверка правил и журналирование

- Проверить корректность сценариев:
  - валидный файл;
  - неверное имя;
  - неверный путь;
  - повторное сохранение с игнорированием нарушения.
- Проверить сохранение записей в `SQLite`.
- Проверить загрузку журнала в `Desktop`.

Результат дня:

- сквозной сценарий от сохранения до отображения в UI работает.

### День 4. Подготовить слой интеграции ELMA

- Уточнить способ авторизации и доступный API `ELMA`.
- Добавить отдельную конфигурацию для `ELMA` вместо привязки только к mock.
- Подготовить `RealElmaClient`.
- Заложить обработку ошибок сети, таймаутов и пустых ответов.

Результат дня:

- кодовая база готова к реальному подключению `ELMA`.

### День 5. Подключить реальный API ELMA

- Реализовать запросы к `ELMA`.
- Научить модуль получать данные клиента и заказа.
- Проверить сопоставление данных заказа с именем файла и путем хранения.
- Сохранить диагностические логи для интеграции.

Результат дня:

- `ELMA` реально участвует в обработке файла.

### День 6. Довести бизнес-валидацию на реальных данных

- Привязать проверки имени и структуры каталогов к данным `ELMA`.
- Обработать кейсы "заказ не найден", "клиент не найден", "тип продукта не совпадает".
- Проверить корректные пользовательские сообщения.

Результат дня:

- сценарий проверки опирается на реальные бизнес-данные.

### День 7. Дубликаты и надежность обработки

- Перепроверить поиск дубликатов.
- Проверить переименование дубликатов.
- Уточнить, нужен ли отдельный пользовательский сценарий удаления.
- Добавить защиту от повторной обработки одного и того же файла в коротком интервале.

Результат дня:

- сценарии дубликатов воспроизводимы и понятны.

### День 8. Подготовить интеграцию GigaChat

- Спроектировать конфигурацию и интерфейс реального клиента `GigaChat`.
- Уточнить формат запроса и ответа.
- Определить, будет ли тегирование происходить автоматически или через подтверждение пользователя.

Результат дня:

- готова кодовая точка подключения реального `GigaChat`.

### День 9. Реализовать реальное тегирование

- Подключить реальный вызов `GigaChat`.
- Нормализовать ответ в формат тегов `ключ-значение`.

Результат дня:

- теги реально формируются не mock-логикой.

### День 10. Довести пользовательский сценарий работы с тегами

Результат дня:

### День 11. Доработать Desktop UI

- Привести экран журнала к рабочему виду.

Результат дня:

Первый рабочий этап:

2. проверяем, что событие гарантированно доходит до оркестратора;
3. только после этого переходим к реальной интеграции `ELMA`.
